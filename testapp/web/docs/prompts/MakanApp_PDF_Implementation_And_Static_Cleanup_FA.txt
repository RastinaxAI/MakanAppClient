۱) ریشه‌یابی پیش از تغییر
نقشهٔ import استایل‌ها، componentها، shellها، theme، CSS Modules، کلاس‌های Tailwind، cn/cva/tailwind-merge و وابستگی‌های build را مشخص کن. این موارد مشاهده شده‌اند و باید مصرف واقعی‌شان دوباره بررسی شود:
- src/app/layout.tsx هم‌زمان globals.css، tokens.css، v5-author.css و v5-product.css را وارد می‌کند.
- در globals.css تعریف‌های پایهٔ heading/input و بازتعریف‌های بعدی وجود دارند؛ مثلاً h1 ابتدا ۲۶ و بعد ۲۸ پیکسل است.
- در messenger.module.css استایل‌های هم‌نامِ پایه در چند نقطه بازتعریف شده‌اند؛ breakpointهای عمدی را با override متعارض اشتباه نگیر.
- بعضی selectorهای مرجع، مانند .rx-root.kind-chat، کلاس وضعیت را روی root می‌خواهند، در حالی که محصول kind را روی section داخلی قرار می‌دهد. رفتار لازم را مطابق DOM واقعی منتقل کن.
- تفاوت‌های framework، role، داده و state را با خطای CSS مخلوط نکن. برای هر اختلاف، DOM، computed style، قاعدهٔ برنده، فایل/خط و مستطیل عنصر را ثبت کن. اسکن ایستا به‌تنهایی علت همهٔ اختلاف‌های بصری را ثابت نمی‌کند.

۲) معماری استایل مقصد
پیشنهاد اجرایی این پروژه، CSS معمولی داخل CSS Modules، همراه با توکن‌های مشترک و global CSS حداقلی است. Next.js را عوض نکن و پروژه را از نو نساز.
- فونت، reset ضروری، متغیرهای تم و قواعد واقعاً عمومی تنها مالک مشخص داشته باشند.
- برای Button، Input، Card، Dialog، Tabs، Navigation و هر shell، کامپوننت و variant مشخص بساز؛ یک property را هم‌زمان در چند فایل و utility کنترل نکن.
- هر بخش را همراه با حذف قواعد قبلیِ جایگزین‌شده منتقل کن. به انتهای stylesheetها وصله‌های بیشتر اضافه نکن. CSS Modules هم در صورت تعریف متعارض در یک فایل، مشکل cascade را حل نمی‌کند.
- CSS اختصاصی صفحه را در root عمومی وارد نکن. CSS اطلس را بدون تطبیق selectorها و DOM در محصول پخش نکن. stylesheet مرجع را پس از انتقال کامل مصرف‌کنندگان از اجرای محصول خارج کن؛ خود مرجع را برای مقایسه حفظ کن.
- Tailwind علت اثبات‌شدهٔ همهٔ اختلاف‌ها نیست. ابتدا مصرف واقعی و Preflight را بررسی کن. utilityهای باقی‌مانده باید مالکیت و cascade مشخص داشته باشند. اگر پس از مهاجرت مصرف مؤثری نماند، import، plugin و وابستگی‌های بدون مصرفش را با lockfile هماهنگ حذف کن. reset و رفتار وابسته را پیش از حذف جایگزین کن.
- از !important انبوه، selector طولانی برای شکست‌دادن CSS قبلی و مخفی‌کردن سرریز برای پوشاندن ایراد استفاده نکن. لایه‌بندی لازم را روشن و متمرکز تعریف کن.

۳) پیاده‌سازی مرجع
قاب داخلی هر دستگاه معیار است. سند A2، قاب گوشی، home indicator ترسیمی، ستون مقایسه، شماره صفحه، توضیحات اطلس و ابزار مرورگر طراحی وارد محصول نشوند. محصول در viewport واقعی ساخته شود؛ zoom، transform یا تصویر کوچک‌شده جای responsive واقعی را نگیرد.
- RTL، Vazirmatn معتبر، وزن و line-height درست؛ تم روشن و تاریک از توکن مرجع، با حفظ ترجیح کاربر.
- موبایل ۳۲۰ تا ۷۶۷: یک ستون و حاشیهٔ مرجع؛ ناوبری پنج‌مقصدی فقط در موقعیت مجاز. متن ۲۰۰٪ ناوبری مجاز را ۳+۲ می‌کند.
- تبلت ۷۶۸ تا ۱۱۹۹: ریل ۷۶ و بازچینی مخصوص همان حالت.
- دسکتاپ از ۱۲۰۰: ناوبری ۲۰۸، حاشیهٔ معمول ۲۶، gap پنل ۲۴، پنل زمینهٔ معمول ۲۸۰ و سقف فضای کاری ۱۵۳۶. استثناهای AuthLayout، ChatWorkspace، جدول و ویرایشگر را از همان شناسه استخراج کن.
- ورودی حداقل ۴۸ و هدف تعاملی حداقل ۴۴ پیکسل CSS؛ اندازهٔ نقاشیِ کنترل و محدودهٔ لمس را در صورت نیاز جدا پیاده کن.
- ابتدا MK-02 و MK-03، MK-170 پیام‌ها، MK-11 فوق‌برنامه، MK-38 دستیار، MK-95 فرم، MK-455 مدیریت کلاس و MK-179 گفتگو را تثبیت کن؛ سپس همهٔ حالت‌های قابل اجرای ماتریس را در تمام بخش‌ها دنبال کن. چند صفحهٔ نمونه پایان کار نیست.
- کلاس سازمانی و کلاس مستقل، نقش‌ها و مجوزهایشان جدا بمانند. قابلیت پیشنهادی تکلیف/آزمون مستقل را فعال نکن. داده‌های اشخاص، شمارها و پاسخ‌های اطلس را به اجرای معمول تزریق نکن؛ fixture فقط در محیط توسعه/تست و با همان کامپوننت واقعی باشد.
- خطای اشتراک یا سرویس دستیار، با تغییر ظاهر رفع نمی‌شود؛ موفقیت API، اشتراک، payer، ingest یا پاسخ AI را جعل نکن. مانع سرور را دقیق و جدا گزارش کن.

۴) کنترل تصویری و رفتاری
برای اثبات طراحی، خود برنامه را در مرحلهٔ بررسی تصویری اجرا کن؛ مشاهدهٔ PDF یا پاس‌شدن build کافی نیست.
- قبل، مرجع و بعد را با شناسه، role، theme، state، داده، focus و اندازهٔ CSS یکسان ثبت کن. تعداد ردیف متفاوت، شاهد برابری هندسی کامل نیست.
- اندازه‌های اصلی: 390×844، 834×1112 و 1440×1000.
- عرض‌های مرزی: 320، 360، 390، 430، 768، 834، 1024، 1194، 1280، 1440 و 1920؛ متن ۲۰۰٪، ارتفاع کم، عنوان و نام فایل بلند و متن ترکیبی فارسی/لاتین نیز بررسی شوند.
- اختلاف ۴ پیکسل CSS یا بیشتر در مستطیل‌های کلیدی را اصلاح کن یا استثنای مستند بده. پیش از ادعای تطبیق، همان اختلاف را دوباره اندازه بگیر.
- ناوبری، حفظ پیش‌نویس، فیلتر، انتخاب، keyboard/focus، Escape و پنجره‌ها را بررسی کن. در پایان build و بررسی‌های موجودِ مرتبط را اجرا کن و CSS خروجی production را نیز ببین.
- برای هر دسته، build و وضعیت واقعی پوشش ثبت شود؛ تصویر قدیمی را به build جدید نسبت نده. بدون شاهد نگوی pixel perfect یا همهٔ حالت‌ها تأیید شده‌اند. تست ظاهری، مجوز ارسال پیام/دعوت، OTP انبوه، خرید یا تغییر مجوز واقعی نیست.

۵) پاک‌سازی بدون اجرای برنامه
این زیرمرحله را با خواندن فایل‌ها، تحلیل AST و جست‌وجوی وابستگی انجام بده. برای تصمیم حذف، dev server، فایل‌های کاندید، generator، migration، seed یا اسکریپت ناشناخته اجرا نکن. build/lint/test مربوط به مرحلهٔ اعتبارسنجی جدا هستند؛ اگر اجرای آن‌ها هم مجاز نیست، نتیجه را «بررسی ایستا؛ سلامت اجرایی تأیید نشده» ثبت کن.
- فهرست فایل‌ها را به runtime، تست، ابزار، قرارداد/codegen، assets، مرجع طراحی، خروجی بازتولیدشدنی و نامشخص تقسیم کن. خارج از runtime بودن به معنی اضافه‌بودن نیست.
- گراف مصرف باید conventionهای Next، page/layout/route/loading/error، proxy/instrumentation، import پویا، barrel، alias، URL رشته‌ای، public، url() و font در CSS، service worker، تنظیمات، package scripts، Docker/Compose، تست و fixture را پوشش دهد.
- نبود import مستقیم یا نبود selector در JSX، دلیل کافی حذف نیست. کلاس‌های پویا و variantها را بررسی کن. گزارش ممیزی موجود فقط نقطهٔ شروع است؛ نام v4، reference، Vite یا old به‌تنهایی حکم حذف نیست. وابستگی انتقالی Vite در Vitest با اپ Vite بازنشسته یکی نیست.
- برای هر کاندید، مسیر، حجم، نقش، مصرف‌کنندگان، دلیل، درجهٔ اطمینان و اثر حذف را در manifest ثبت کن. موارد اثبات‌شده را حذف کن؛ موارد مبهم را نگه دار و علت را گزارش کن. هدف رسیدن به عدد دلخواهِ فایل حذف‌شده نیست.
- پیش از حذف سورس/اسناد منسوخِ اثبات‌شده، نسخهٔ قابل بازیابی را بیرون workspace با hash و راه بازیابی نگه دار؛ importها، scriptها و لینک گزارش‌های مرتبط را اصلاح کن. فایل‌های تولیدیِ غیرفعال و واقعاً بازتولیدشدنی با رسید قابل پاک‌سازی‌اند. فایل‌های build مورد مصرف اجرای فعال حذف نشوند.
- .envها، اسرار، نشست‌های محلی، Docker volume، دادهٔ کاربر، migration معتبر، قرارداد API، فونت/لوگوی فعال، تست‌های معتبر، مرجع V5 و شواهد لازم را حفظ کن. محتوای secret را چاپ نکن.
- برنامهٔ مالک در sibling جداست. فایل‌های بیرون این کلاینت را حذف یا بازنویسی نکن. اپ Vite ریشه بازنشسته است؛ آن را برنگردان. launcher ریشه و Compose معتبر حفظ شوند. git clean -fdx، reset --hard و حذف کور پوشه‌ها اجرا نکن. تست را برای سبزشدن نتیجه حذف نکن.

۶) تحویل و معیار اتمام
کد واقعی اصلاح‌شده، preview محصول، نگاشت به‌روز همهٔ ردیف‌ها، تصاویر هم‌اندازه، گزارش propertyهای متعارض و راه‌حلشان، manifest پاک‌سازی و نتیجهٔ بررسی‌ها را تحویل بده. پوشش ظاهری، صحت رفتار/API و حذف فایل‌های بدون مصرف سه نتیجهٔ جدا هستند؛ موفقیت یکی، اثبات دیگری نیست.
تصمیم‌های معمول را خودت بگیر و مرحله‌به‌مرحله اجازه نخواه. تا تمام اصلاحاتِ قابل انجام پیش برو؛ برای مانع واقعی، وابستگی و حالت‌های متأثر را دقیق ثبت کن. در web/docs/PROGRESS.md نتیجه و محدودیت‌ها را بنویس. صرف تغییر رنگ، تمیزکردن کش یا پاس‌شدن build را اتمام تطبیق PDF معرفی نکن.
